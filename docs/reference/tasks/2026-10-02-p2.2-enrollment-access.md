## User outcome

A parent enrolls their child in published courses that the child is eligible for (age, Pod membership, subscription status). The mobile app can then present a filtered "available courses" list scoped to what the specific child can actually access, and the parent sees the child's current enrollment history. This is the gate that turns the public catalogue into a personalized learning path while enforcing child safety and subscription entitlements server-side.

## Scope

- Migration `course_enrollments` with unique `(child_id, course_id)`, status/source enums, and indexes.
- Enums `EnrollmentStatus` and `EnrollmentSource` in `App\Domain\Learning\`.
- `Enrollment` model, factory, and `EnrollmentPolicy`.
- `CourseAccessService` — evaluates published/age/Pod/subscription eligibility.
- `AccessDecision` value object with typed reason codes.
- `EnrollChildInCourse` domain action — idempotent enrollment with access validation.
- API endpoints: POST enrollments, GET enrollments, GET available-courses.
- Request validation, response resources, OpenAPI update, feature tests.

## Non-goals

- Lesson delivery, progress tracking, and completion (P2.3).
- XP, badges, or rewards triggered by enrollment (P2.6).
- Admin manual enrollment UI (the action supports `source:manual` but no Filament resource here).
- `camp`/`school` enrollment flows (enum values reserved, no logic).
- Unenrollment or transfer between courses.
- `pod_courses` many-to-many (deferred per P2.1).

## Journey and states

1. Authenticated parent requests available courses for a child: the API filters published courses where child age matches eligibility band, child has active Pod membership on course.pod_id, parent has active subscription OR course is free_preview, and child is not already enrolled. Returns paginated list or empty.
2. Parent enrolls child in a course by POSTing course_id: system validates all access rules, creates enrollment with status=active and started_at=now. Duplicate enrollment returns existing record (200). Ineligible returns 403 with machine-readable reason code.
3. Parent lists enrollments: returns the child's enrollment history ordered by started_at descending.
4. Access-expiry edge: existing enrollments persist after subscription expires; this package only blocks NEW enrollments. Lesson-playback revocation is P2.3.
5. Free-preview: courses flagged is_free_preview bypass subscription check but still require Pod membership and age eligibility.
6. Validation errors: missing/invalid course_id returns 422. Child not owned returns 403 from policy.
7. Cross-household: parent cannot see or modify another family's enrollments (ChildPolicy ownership check).

## Data, API, and authorization

- Table `course_enrollments`: child_id FK restrict, course_id FK restrict, enrolled_by_parent_id FK restrict, unique(child_id, course_id). Status is indexed varchar, source is varchar. No cascade deletes — enrollments are learner history that must never be silently removed.
- Endpoints require Bearer token (Sanctum) + authenticated parent who owns the child (ChildPolicy). No write authorization beyond ownership; enrollment cannot be performed by the child directly.
- Response envelope: success/message/data + meta/links for lists.
- Available-courses eager-loads track + pod to avoid N+1; query count guarded in tests.
- No child PII in enrollment response beyond child_id + course metadata (parent already owns child).
- SubscriptionAccessService delegates subscription validity; P2.2 does not duplicate that logic.

## Risks and decisions required

- Risk: Pod membership requirement means a child cannot access any course unless they've joined the Pod first. The onboarding flow (P1.3A) must complete before enrollment is possible. Mitigated: free_preview courses still require Pod membership, making the onboarding flow a hard prerequisite.
- Decision: enrollment is per-child-per-course unique; a child cannot have multiple enrollments in the same course. If a course is re-released, the same enrollment row persists (status may transition).
