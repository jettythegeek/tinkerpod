# Task specification: P2.1 content schema and admin

- Build package: `P2.1`
- Owner/agent: Qoder
- Date: 2026-09-26
- Relevant PRD sections: 3, 7–9, 10, 11, 13, 18, 20, 24
- Focused specifications: `docs/learning/COURSE_AND_CONTENT_PLAN.md`, `docs/backend/DATABASE_PLAN.md`, `docs/backend/API_PLAN.md`, `docs/admin/ADMIN_DASHBOARD_PLAN.md`, `docs/quality/SECURITY_AND_CHILD_SAFETY.md`
- Design reference: no new visual surface — Filament admin uses the existing `Learning` navigation group and `resources/css/filament/admin/theme.css` brand tokens

## User outcome

A content manager assembles real learning content in the admin panel — tracks, then courses attached to one primary Pod, ordered modules, and ordered lessons of each delivery type — and publishes it only when the structure is complete. A parent-facing client can then read the published catalogue without ever seeing draft or archived material, so curriculum work is safe to do in production while learners only ever meet finished content.

## Scope

- Migration for `tracks`, `courses`, `modules`, `lessons` with slugs, ordering, status lifecycle, eligibility, and indexes.
- String-backed enums for the content vocabularies (`ContentStatus`, `CourseEligibilityLevel`, `LessonType`, `LessonCompletionRule`, `VideoProvider`) mapped onto indexed varchar columns, per `DATABASE_PLAN.md`.
- Models `Track`, `Course`, `Module`, `Lesson` with typed relations and ordering scopes, plus factories for each.
- Domain actions `PublishCourse` and `ArchiveCourse` implementing the publishing workflow with validation that blocks incomplete publication.
- Seeders: the seven tracks plus four published starter courses (Coding, AI, Design, Robotics) with modules and lessons, and one archived example to prove lifecycle filters.
- Filament resources for tracks, courses, modules, and lessons with publish/archive actions and status filters.
- Read-only public catalogue endpoints `GET /api/v1/tracks`, `GET /api/v1/courses`, `GET /api/v1/courses/{slug}` and OpenAPI updates.
- Unit, feature, and migration tests.

## Non-goals

- Enrollments, lesson progress, completion maths, and `has_access` gating (P2.2, P2.3).
- Quiz records, questions, attempts, and scoring (P2.4). `quiz` lessons are publishable; their pass rule resolves in P2.4.
- Private attachment upload, storage disks, and signed URLs (P2.3). Media fields hold provider-neutral URLs only.
- `pod_courses` many-to-many, projects, live classes, XP, badges, and ranks.
- Drag-and-drop reordering: ordering is an explicit `sort_order` value that publish validation and catalogue output depend on.
- Role/permission navigation gating for content resources, which stays absent panel-wide to match existing resources.

## Journey and states

1. Content manager opens Learning → Tracks and sees seeded tracks ordered by `sort_order`; empty state is the Filament default with a create action.
2. They create a course: title auto-slugs, primary Pod and optional track are chosen, eligibility band and level are set, status starts `draft`.
3. They add modules to the course, each with `sort_order`, then lessons to a module, choosing a `lesson_type`; media fields appear per type and are required for that type (video needs a URL, PDF needs an attachment URL, external link needs a URL, text needs content, project instruction needs content, quiz defers to P2.4).
4. They press Publish. If the course lacks a Pod, has no module, a module has no lesson, or a lesson lacks the media its type requires, publishing is refused with a per-problem message and the course stays `draft`.
5. On success the course and all its non-archived modules and lessons become `published`, `published_at` is stamped once, and the catalogue lists the course.
6. Re-publishing an already-published course re-validates and changes nothing visible. Archiving a course hides it and its whole subtree from the catalogue while preserving history for future enrollments.
7. Catalogue reads: an unknown slug, or a slug that exists but is not published, both answer the same 404 envelope so drafts cannot be probed. Empty catalogue returns an empty list, not an error.

Loading, offline, and error presentation belong to the mobile client (P2.5); this package supplies the contract and the states the API must answer.

## Data, API, and authorization

- New tables as scoped above. Every `status` is an indexed varchar defaulting to `draft`; `slug` columns are unique; `sort_order` is an unsigned small integer defaulting to 0.
- `courses.pod_id` and `courses.track_id` are nullable `restrictOnDelete` FKs — Pods and tracks are taxonomy that must never be silently deleted — while `modules.course_id` and `lessons.module_id` are required `cascadeOnDelete` so a draft skeleton can be removed cleanly. `modules` and `lessons` are course structure, not learner history, so cascade is safe pre-P2.2; that becomes restrictive once progress references them.
- Indexes: `(status, sort_order)` on tracks and courses, `(course_id, status, sort_order)` on modules, `(module_id, status, sort_order)` on lessons, plus `(pod_id, status)` and `(track_id, status)` on courses for catalogue filters.
- `published_at` records first successful publication and is never cleared by archive/unarchive.
- Endpoints are public and read-only, return the existing manual `success` / `message` / `data` envelope, expose only `published` rows, filter published courses by `pod`, `track`, `level`, and `age`, and paginate with `meta` and `links`.
- No child, parent, or payment data is exposed, so no new privacy surface. Course detail includes an `access` object with a fixed `requires_subscription: true` so P2.2 can refine it without breaking clients.
- Writes stay in Filament behind the existing `canAccessPanel()` role allowlist; no new API write routes means no new client-side authorization risk.
- Seeding is idempotent through `updateOrCreate`, so `db:seed` twice never duplicates content.

## Design inventory

Admin only: `Heroicon::OutlinedCommandLine` (Tracks), `OutlinedAcademicCap` (Courses), `OutlinedRectangleStack` (Modules), `OutlinedPlayCircle` (Lessons); `Learning` navigation group; brand `#00B8A9` primary from the panel provider; status badges render `draft` gray, `published` success, `archived` danger so lifecycle is never colour-only — each badge also carries its label. No motion, audio, or haptics.

## Acceptance criteria

- [ ] `php artisan migrate:fresh --seed` succeeds on MySQL 8.4 and leaves seven tracks and four published starter courses with modules and lessons.
- [ ] The migration rolls back cleanly and re-applies on a populated database.
- [ ] A course missing a Pod, module, lesson, or required media cannot be published and reports why; the failure leaves no partially published subtree.
- [ ] Publishing marks the course and its non-archived children `published`, stamps `published_at` once, and is idempotent on replay.
- [ ] Archiving a course removes it and its lessons from every catalogue response.
- [x] `GET /api/v1/courses` lists only published courses, honours documented filters, paginates, and never leaks draft or archived titles or ids.
- [x] `GET /api/v1/courses/{slug}` returns ordered published modules and lessons with durations and completion rules, and 404s for unpublished or unknown slugs.
- [x] Course detail loads without N+1 queries (guarded by a query-count assertion).
- [ ] Content manager sees Tracks, Courses, Modules, and Lessons in the Learning group and can perform the full journey in the panel.
- [ ] Focused and full test suites pass; Pint reports no violations.

- Visual/device: admin panel at desktop width and a narrow tablet width; screenshot the course form, lesson form, and courses table with all three statuses visible.
- Accessibility/security: confirm badges carry text not colour alone; confirm the catalogue responses contain no child identifiers; confirm cross-status probing by draft slug returns 404.

## Risks and decisions required

- Approved 2026-09-26: content eligibility uses `minimum_age`, `maximum_age`, and `experience_level` rather than the PRD's `age_group` and `learning_level` strings, so catalogue matching reuses the shipped `PodRecommendationService` age-range rule instead of forking a second vocabulary.
- Approved 2026-09-26: `courses.pod_id` is nullable in the database but required by publish validation, since the PRD table omits it while `COURSE_AND_CONTENT_PLAN.md` and the Pod-first product invariant require it.
- Approved 2026-09-26: P2.1 ships the read-only catalogue API so the package is one vertical slice.
- Risk: existing tables store vocabularies as raw strings. Introducing enums only for new content tables is a deliberate, documented divergence; the alternative is rewriting shipped migrations, which this package must not do.
- Risk: seeded starter curriculum is authored placeholder material. It is marked as seed content and needs editorial approval before real learners see it.
